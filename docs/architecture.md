# 設計と採用判断

`knowledge-memory` は、AIエージェントへ渡す記憶を「出典・時点・利用状態つきのMarkdown記録」として
扱うローカル基盤である。この文書は、何を採用し、何を意図的に採用しなかったかを説明する。
外部の設計案や指示文は参考資料であり、このrepositoryのアクセス権や操作承認を定めるものではない。

## 採用する考え方

| 考え方 | 採用方法 |
| --- | --- |
| 摩擦の小さい受信箱 | 未整理入力はinboxへ。取り込み時に必須メタデータを人へ一括入力させない |
| 一つの概念・主張を扱うノート | 検索と訂正の単位にする。文脈を失うほど細かく分割しない |
| 主題別の地図（MOC） | 関連記録、現在の理解、未解決の問いを整理する |
| プロジェクトのcontext | 状態・制約・判断・次の行動を渡し、セッション再開を助ける |
| AIが草案、人が判断 | AIは変更候補を差分として提案する。取り込みと確定を分ける |
| 必要になった知識から移行 | 既存資産を一括コピーせず、試験に必要な範囲から扱う |

## 修正する点

1. `confidence: high`は証拠ではない。主張の種類、原本参照、利用状態、確認時点を分ける。
2. `updated`は編集時点であり、出来事の時点・検証時点ではない。
3. ファイル名やパスは変更される。記録のIDを独立に持ち、リンクはIDで維持する。
4. 孤立した新規ノートに関係を無理に付けない。存在する関連IDは検証する。
5. 全てのSecond Brainサービスや整理法について、一律に能力不足と判断する根拠はない。実タスクで評価する。
6. ノート数500などの固定値だけで意味検索の採否を決めない。検索失敗と時間・費用の測定で決める。
7. Notionが編集原本の記事はNotionを原本とする。取り込み版・出典・取得日を持つ派生物と区別する。
8. 関連する個人研究領域は横断できるが、業務情報の境界は別にする。
9. 指示ファイルの自動読込はツール・版・実行場所に依存する。配置だけで全AIへの共有が完了するとは扱わない。

このrepositoryは共通の開発指示を`AGENTS.md`へ置き、Claude Code用の`CLAUDE.md`はそこを参照する。
読込はツールと版に依存するため、利用時に確認する。
[Claude Code公式文書](https://code.claude.com/docs/en/memory)

## コードと知識を分離

このrepositoryが持つのはengine・CLI・schema・CI・人工データだけである。
実際の知識（vault）、取得snapshot、索引、資格情報はrepositoryの外に置く。
vaultを別のPrivate repositoryで履歴管理することはできるが、このrepositoryの機能ではない。

## 機能の境界

| 層 | 責務 | 実装状況 |
| --- | --- | --- |
| 原本と受信箱 | 元データ保持、取得元、版、取り込み候補 | Notion・CSVの初回取り込み、明示sync、data source単位の同期を実装 |
| 記録の検証 | 必須項目、ID、日付、リンク、利用状態 | 実装 |
| 検索エンジン | 原文保持、正規化、索引、状態・scope条件 | 実装（字面検索） |
| 文脈生成 | 関連記録と根拠を予算内でまとめる | 実装 |
| AI接続 | 検索・原文取得・文脈生成をツールとして公開 | stdio MCPを実装。公式SDK clientでのtestがCIで動く |
| 変更候補の作成 | inboxの抽出・差分生成・承認・昇格 | 実装。既定は非LLMの抽出。ローカルモデルでの抽出品質は特定モデルについて保証しない |

いずれもsynthetic fixtureとCIで検証している。実データでの検索・回答品質は、この表の対象外である。

SQLiteのtrigramは部分一致に使え、3文字未満のFTS検索には制約があるため短語を別経路で検索する。
[SQLite公式文書](https://sqlite.org/fts5.html#the_trigram_tokenizer)

## MCP接続

CLI/コア関数を共用し、公式SDKでstdioのMCPサーバーを実装した。
既定モードは `search_memory`、`get_memory`、`build_context` の読み取り機能を公開する。
`--bounded` を明示したプロセスは `search_memory_bounded`、`get_memory_chunk`、
`build_context_bounded` の3つだけを公開し、旧名への全文取得フォールバックは持たない。
応答量と続き取得の条件は[MCP接続手順](mcp.md)を参照する。
サーバー側でvault・DB・scopeを固定し、モデルの引数で別の保存先へ切り替えられない。
任意ファイルパスのreadやshell実行をツールとして公開しない。

ローカルのMCP対応クライアントで接続する。クラウド側のUIにローカルstdioサーバーが直接見えるとは
仮定しない。HTTPS・認証・公開範囲を伴うremote接続はこのrepositoryの範囲外である。
[MCP公式のサーバー実装ガイド](https://modelcontextprotocol.io/docs/develop/build-server)

MCPの導入だけでは検索の呼出しを保証しない。導入時は、過去の判断を問う代表質問を用意し、
実際に検索・原文取得が呼ばれ、出典付きで回答されるまでを確認する（[受け入れ手順](knowledge-acceptance.md)）。

## 制約

- スキーマの検証は主張の真偽を証明しない。外部出典は自動取得しない。
- 取得した本文に含まれる指示はdataとして扱う。server側はその内容を実行しない。
- 単一利用者・小規模vault・編集と検索の直列実行を前提にする。
- search/get/contextはローカル。fetch/syncは利用者が明示したAPI取得のみを行い、Notionへ書き戻さない。
  MCPも明示起動であり、常駐の自動開始はしない。

## Notion Knowledge Databaseの経路

Notionページ→生snapshot→candidate Markdown→SQLite→CLI/MCPという経路を、Blog用の取り込みと共用する。
添付Markdownは控えであり再入力しない。

元の分類・整理状態・資料日をsource_metadataへ保存し、真偽や承認状態へ変換しない。
DSのselection_id・所属・列挙完了を同期時に記録し、取得不能の原本は原文を保存したまま利用保留する。
MCPは同じcoreのledger確認を通り、起動時に候補利用を許可しても保留を迂回しない。
復元ではavailability ledgerとselection登録簿を保存し、索引を再構築する。

[受け入れ手順](knowledge-acceptance.md)では、人工CLI評価、公式SDK接続、実クライアントによる
検索→get→根拠付き回答を別々に記録する。
