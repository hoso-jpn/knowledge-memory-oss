# Blog・個人Knowledge・業務資料の境界

## 境界の考え方

公開用・個人用・業務用の資料は、scopeによる絞り込みだけでなく、選択・保存先・プロセス・資格情報を分けて扱う。
`km-profile`はその分離を配備前に検査する。下表は推奨する構成例である。

| プロファイル | 選択 | 保存・参照 | 目的 |
| --- | --- | --- | --- |
| Blog | 公開用DB内の承認したページだけ | 専用vault/index/state/プロセス | 公開記事を個人・業務の資料と混ぜない |
| 個人Knowledge | 個人用と人が判断したページだけ | 専用vault/index/state/プロセス | 学習・判断の記録を個人の範囲に保つ |
| 業務 | 業務用と人が判断したページだけ | 専用vault/index/state/プロセス・資格情報 | 業務資料を個人用のAI接続から到達させない |
| 分類不明 | 保留 | どのallowlistにも加えない | 自動分類しない |

Notionのビューやdata sourceは認証境界の代わりにならない。権限分離が必要なら別Databaseと
接続権限を基本案とし、Notion側の変更は別の移行計画で扱う。scopeは論理フィルターである。
同じOS利用者が全ファイルを読める構成をこの検査でアクセス隔離済みとは呼ばない。

## 通信・書き込みを行わない事前検査

[`examples/profiles/`](../examples/profiles/)は架空ID・架空の外部パスによる3プロファイルと、未分類1件の例。
実運用ではリポジトリ外へコピーし、私的なID/保存先へ置き換えて管理する。

```bash
km-profile --config /outside/config/profiles.yaml --inventory /outside/config/inventory.json
```

inventoryは読み取り棚卸しで得たページIDのローカルJSON配列。コマンド自身はNotionへ接続せず、
ディレクトリも作らない。指定がなければinventory未提供と表示し、空の棚卸しを完了と扱わない。
未知のIDをheld_unselectedへ残し、タイトル・分野・candidate/activeから分類を推測しない。
出力には私的IDが含まれ得るため、GitHubへ転載しない。

検査は名前・scope・selection_id、候補参照設定、保存先の重複と包含、symlink解決後の同一性、
ページIDの表記差を正規化した重複、設定とのscope不一致を拒否する。
混在DBを全件取得しないため、この初期プロファイルではNotionのexact page allowlistだけを許す。
DS全体の選択には、含まれる全資料と将来追加資料の境界について別の導入レビューが必要。
GitHubの明示ファイル選択は既存sync設定どおり扱う。owner/repository名の大文字小文字を正規化して
重複を検査し、ファイルパスの大文字小文字は保持する。同じ原本を複数プロファイルに選ばない。

このコマンドは配備前検査であり、既存サービスを再構成・停止しない。
検査を通った設定のvault/index/scope/include_candidatesを各プロセス起動時に固定し、
同じ設定でsync→index→MCPを運用する。モデルのツール引数では変更できない。
既存のkm-sync/km-mcpを直接起動すれば、この設定検査が自動で挟まるわけではない。
常用の運用手順は[管理運用](managed-runtime.md)、応答上限は[bounded mode](mcp.md)を参照する。

## 分類や所属を変更するとき

1. 原本を動かす前に、旧/new allowlist、索引、常駐プロセス、キャッシュ、バックアップの対応を記録する。
2. 旧プロファイルの通常参照を止め、旧allowlistから外して同期する。既知の資料がunselected等の
   利用保留になり、再索引後もsearch/get/contextから返らないことを確認する。
   **最後の1件を外す場合はこの同期手順を使えない。** 現行syncは空の`sources: []`を拒否し、
   既存ledgerを変更しない。旧プロファイルの定期実行と全参照プロセスを停止したまま廃止し、
   クライアントの接続先からも外す。旧vault/index/stateとバックアップは通常参照から隔離して保持する。
   空allowlistによる失効を確認済みとは扱わず、旧サービスを再開しない。
3. 新プロファイルの設定を検査し、新規の保存先でdry-run、許可された取得、索引、参照を確認する。
   原本の削除や既存ノートの無条件コピーを移行手段にしない。
4. 旧資料は履歴として保持する場合も、通常の検索対象へ戻さない。旧DBだけを再利用しない。
   ノートとledger/registryを組として復旧し、現行allowlistと照合してから再接続する。
5. 途中で失敗したら新プロファイルを接続せず停止し、旧側の利用保留を保持する。
   古いバックアップを戻すだけで失効した資料を再公開しない。
   資料が混在していた旧経路への復帰や、止めた旧い定期実行の再開を戻し方にしない。対象Notion経路を
   クライアントで無効化し、境界を検証した分離構成だけを復旧する。

新経路の境界検査と、利用者が常用する経路の境界は別の条件である。利用するクライアントの接続先・
preset・ツール一覧を新しい会話で確認してから、旧経路のサーバーと再起動手段を停止し、
旧索引・世代を通常参照から隔離する。
旧会話に既に入ったツール結果は切替で消えないため、新規会話の検証と履歴の扱いを分ける。
Notion側のDatabase移動や接続権限分離はこのrepositoryの機能ではない。
設定検査だけで現在の配備が正しいとは判定しない。
